Value or Reference?

int bonus = 5;
auto byValue = [bonus](int score) { return score + bonus; };
auto byReference = [&bonus](int score) { return score + bonus; };

bonus = 10;
cout << byValue(80) << " " << byReference(80) << endl;

Output: 85 90

Have students predict before revealing. The by-value closure copied bonus when the lambda was created, so it still holds 5. The by-reference closure reads bonus at the call, after it became 10.

Silent Conversions

  • Built-in types convert to each other without being asked.
  • Some conversions lose data: double to int drops the fraction.

Conversion Operator Anatomy

class Temperature {
private:
    double celsius;

public:
    Temperature(double value = 0.0) { celsius = value; }

    operator double() const { return celsius; }

    return 0;
}

Output: 21.5 23

Which Constructors Convert from One Value?

Constructor Converts a single value?
Temperature() No: takes nothing
Temperature(double c) Yes: double to Temperature
Temperature(double c = 0.0) Yes: the default does not matter
Temperature(double c, char unit) No: needs two values
Temperature(double c, char unit = 'C') Yes: the second parameter has a default

Since C++11 any constructor that is not explicit also takes part in brace initialization, so Temperature t = {21.5, ‘F’}; uses the two-argument constructor. The table covers conversion from one value, which is the case that happens silently.

What the Compiler Builds

  • Temperature today = 21.5; asks for a Temperature built from 21.5.
  • The compiler calls Temperature(double) to build it.
  • No constructor call appears in the source code.

Formally the rule builds a temporary Temperature and initializes today from it. Since C++17 that copy is guaranteed to be skipped, which is why the program printed one constructor call, not two.

Object Conversions

Can One Class Become Another?

  • Fahrenheit report = today;

Slides 29–37

Fahrenheit is a new class that stores degrees Fahrenheit. today is still the Celsius Temperature.

Two Places to Put the Conversion

In the target: a converting constructor

class Fahrenheit {
private:
    double degrees;

public:
    // Built from a Temperature
    Fahrenheit(const Temperature& t);
};

In the source: a conversion operator

class Temperature {
private:
    double celsius;

public:
    // Becomes a Fahrenheit
    operator Fahrenheit() const;
};

Both make Fahrenheit report = today; compile. The next slide decides between them.

Which One to Write?

Converting constructor Conversion operator
Lives in Fahrenheit, the target Temperature, the source
You must be able to edit The target class The source class
  • Write both and the compiler may reject Fahrenheit report = today; as ambiguous, or quietly pick one.
  • Write one, in the class you own. When you own both, prefer the constructor: the class being built controls how it is built.

Tested with g++: with only the two conversions, g++ reports the conversion as ambiguous. Add Temperature’s operator double and the same line compiles with no warning and uses the constructor. Either way, the author no longer controls which conversion runs.

Temperature to Fahrenheit

class Temperature {
private:
    double celsius;

public:
    Temperature(double value = 0.0) { celsius = value; }
    operator double() const { return celsius; }
};

class Fahrenheit {
private:
    double degrees;

public:
    Fahrenheit(double value = 32.0) { degrees = value; }

    // Converts a Celsius Temperature to Fahrenheit
    Fahrenheit(const Temperature& t) { degrees = t * 9.0 / 5.0 + 32.0; }

    double value() const { return degrees; }
};

int main() {
    Temperature today(20.0);
    Fahrenheit report = today;
    cout << report.value() << endl;
    return 0;
}

Output: 68

The constructor reads the Celsius value through operator double from topic 2: t * 9.0 converts t to double first.

Four Places Conversion Happens

    Temperature today(20.0);
    Fahrenheit a = today;              // copy initialization

The Constructor Hijacked the Call

  • The caller meant section 30.
  • showSection needs a Roster, and Roster(int) can build one from 30.
  • The compiler built a 30-seat roster and passed it in.
  • No error, no warning, wrong output.

explicit Constructors

explicit Roster(int capacity);

showSection(sectionNumber);    // error: no conversion from int
showSection(Roster(30));       // fine: the conversion is written out

The standard library does the same: vector<int> v = 10; does not compile.

g++ reports: invalid initialization of reference of type ‘const Roster&’ from expression of type ‘int’. vector’s size constructor is explicit for exactly this reason.

Delete the Conversion You Forbid

explicit Roster(int capacity);
Roster(double) = delete;

Roster small(2.7);    // error: use of deleted function

explicit does not stop direct initialization, so without the deleted overload Roster small(2.7); compiles and builds a 2-seat roster. The deleted constructor is an exact match for double, so the compiler picks it and refuses.

explicit Conversion Operators

explicit operator double() const { return celsius; }

double a = today;                       // error
double b = static_cast<double>(today);  // fine
if (freezing) { }                       // error: zero is no longer false

g++ reports the if as: invalid user-defined conversion from ‘Temperature’ to ‘bool’. The cast states the intent, so it is allowed.

Why while (cin >> x) Still Works

  • cin >> x returns cin, and streams define an explicit operator bool().
  • An explicit conversion to bool still happens in conditions and in !, &&, ||, and ?:.
  • Everywhere else it must be written out: bool ok = cin; does not compile.

This is called contextual conversion to bool. The standard library made the stream conversion explicit so that a stream cannot silently become a number or a bool in arithmetic or assignment.

Two Routes, No Winner?

class Temperature {
private:
    double celsius;

public:
    Temperature(double value = 0.0) { celsius = value; }
    operator double() const { return celsius; }

    friend Temperature operator+(const Temperature& a,
                                 const Temperature& b);
};

Temperature t(20.0);
Temperature warmer = t + 5.0;    // compiles?

Ask students to name every way the compiler could make t + 5.0 work before revealing the next slide.

Breaking the Tie

Route Converts Then calls
1 t to double with operator double() Built-in double + double
2 5.0 to Temperature with Temperature(double) Your operator+
  • Each route needs one user-defined conversion, so neither is better and g++ reports an ambiguous overload.
  • Fix: mark operator double() explicit. Route 1 disappears and warmer is 25.

How the compiler chooses an overload: an exact match beats a promotion, a promotion beats a standard conversion, and a standard conversion beats a user-defined conversion. Two candidates that each need a user-defined conversion on different arguments tie, which is an error.

Full program with the fix: cpp/ambiguous_plus.cpp

explicit by Default

  • Start every one-value constructor and conversion operator as explicit.
  • Remove explicit only when topic 4’s test passes: the target names the meaning and nothing is lost.
  • Use = delete for the specific types you want to forbid.

C++ Core Guidelines C.46: by default, declare single-argument constructors explicit. C.164: avoid implicit conversion operators.

Summary

  • explicit turns a silent conversion into one the caller must write.
  • = delete forbids a conversion outright; together they make every conversion intentional.

Operator Chaining

Chains You Already Wrote?

  • cout << a << b; (07.02)

Slides 51–60

Two Kinds of Chains

Operator Changes its left operand? Returns
+ No A new object, by value
= and += Yes The left operand, by reference
<< Yes, the stream The stream, by reference
  • Each link in a chain works on whatever the previous link returned.

Why << Must Return a Reference

  • cout << a << b groups as (cout << a) << b.
  • The second << must write to the same stream as the first.
  • Streams cannot be copied, so returning ostream by value does not compile.

g++ rejects an operator<< that takes and returns ostream by value: the stream’s copy constructor is not accessible. The reference is not a style choice here; it is the only option.

You Have Written return *this Before

Temperature& operator+=(const Temperature& rhs) {
    celsius += rhs.celsius;
    return *this;
}
Part Why
Temperature& Hands back the object itself, not a copy
const Temperature& rhs The right side is read, never changed
return *this; this points to the left operand; *this is that object

Students wrote the same three parts in 08.02’s copy assignment operator. Frame this as why that code works rather than as new syntax.

+= That Chains

class Temperature {
private:
    double celsius;

public:
    Temperature(double value = 0.0) { celsius = value; }

    Temperature& operator+=(const Temperature& rhs) {
        celsius += rhs.celsius;
        return *this;
    }

    friend ostream& operator<<(ostream& out, const Temperature& t);
};

int main() {
    Temperature a(20.0);
    Temperature b(5.0);

    cout << (a += b) << " " << a << endl;
    return 0;
}

Output: 25 25

Both values are 25 because (a += b) is a itself. The definition of operator<< is in the full program.

Never return a reference to a local variable: an operator+ that returns Temperature& to its local result leaves a dangling reference, and g++ warns with -Wreturn-local-addr.

The operator or member function Returns

Unit Testing

Slides 62–78

This topic completes the debugging sequence: structured debugging in 08.02, assertions in 09.01, and now tests that rerun the checks on purpose.

You Already Wrote the Checks

  • The assertions from the Invariant Lab stop the program when a rule breaks.
  • They only check code the program happens to run: nothing forces a call to highestScore when the largest score is last.
  • A unit test chooses the inputs on purpose, so the check runs every time the tests run.

What Is a Unit Test?

  • Unit: the smallest testable piece of a program, usually one function or member function.
  • Unit test: code that calls a unit with known input and compares the result with an expected value worked out by hand.
  • Test suite: all of a program’s tests, run together.

Tests can only call public members. scores and count are private, so every test goes through the class’s public interface. That is encapsulation paying off: a test checks the promises a class makes, not how it keeps them.

Parts of a Unit Test

Arrange builds the situation, Act calls the function under test, and Assert checks the result. Assert is only the step’s name: check() is an ordinary function, and the assert macro is not involved.

bool testHighestScoreIncludesLastElement() {
    // Arrange: build a gradebook whose largest score is last
    Gradebook book;
    book.addScore(88);
    book.addScore(72);
    book.addScore(95);
    book.addScore(99);

    // Act: call the function under test
    int result = book.highestScore();

    // Assert: check the result against the value worked out by hand
    return check(result == 99, "highestScore includes the last score");
}

Keep the Tests in the Same File

The class, the tests, and the program share one file, so it compiles in any online compiler. One constant at the top decides what main does.

// true runs the unit tests, false runs the gradebook program
const bool RUN_TESTS = true;

int main() {
    if (RUN_TESTS) {
        int failures = runTests();
        return failures == 0 ? 0 : 1;
    }

    runProgram();
    return 0;
}

The tests check the real class, not a copy. Pasting the class into a second file would create two versions that drift apart, which defeats the purpose. Professional projects put tests in separate files, which students will see later.

// Print one test result and return whether it passed
bool check(bool condition, const string& testName) {
    if (condition) {
        cout << "PASS  " << testName << '\n';
    } else {
        cout << "FAIL  " << testName << '\n';
    }
    return condition;
}

// Run every test, keep going after a failure, and report the total

Compare Doubles Within a Tolerance

average() returns a double, and 250 / 3 cannot be stored exactly. Testing it with == can fail a correct program, so the test asks whether the result is close enough.

// Doubles are compared within a tolerance, never with ==
bool closeEnough(double actual, double expected, double tolerance) {
    return fabs(actual - expected) <= tolerance;
}

bool testAverageOfThreeScores() {
    Gradebook book;
    book.addScore(90);
    book.addScore(85);
    book.addScore(75);

    // 250 / 3 = 83.333..., which a double cannot store exactly
    return check(closeEnough(book.average(), 83.333, 0.001), "average of 90 85 75 is about 83.333");
}

Connect to the lambda review: toWhole(3.9) showed that converting a double can lose information, and comparing doubles with == has the same trap. fabs comes from the cmath header.

A true story from building this slide: the first draft used 90, 85, and 76 and expected 83.333. The test failed, because 251 / 3 is 83.667. The test was wrong, not the code. Expected values must be worked out carefully by hand.

Choose Test Cases at the Edges

  • Bugs gather at boundaries, so test the legal edges: an empty gradebook, one score, a full gradebook, and scores of exactly 0 and 100.
  • Illegal input such as addScore(101) is not a legal edge: every test stays inside each function’s preconditions.

Testing frameworks such as GoogleTest and Catch2 can test that an assertion fires, but this course uses the standard library only. The next slides show what goes wrong when a test breaks a precondition.

In the gradebook, the tests caught the bugs inside the class: the loop that stopped early and the uncapped curve. The assertions caught the bugs in main: the score of 105, and calling average and removeLast on an empty gradebook. The two tools work together.

What If Assertions Are Turned Off?

Test run Compiled normally Compiled with -DNDEBUG
Nine tests, all inside the preconditions 9 run, 0 failed 9 run, 0 failed

  • Tests never rely on assert, and they never break a precondition.

A test that breaks a precondition either stops the whole suite or, with assertions off, puts bad data into the object and reports failures that point at the wrong place.

Write the Test Before the Fix

  1. Write a test that reproduces the bug, and watch it fail.
  2. Fix the code.
  3. Rerun the test, and watch it pass.
  4. Keep the test.

A test that has never failed has never proved it can catch anything. A test written for a bug is a regression test from the day it is written.

Unit or Regression?

Term Answers Means
Unit test What does it cover? One function or member function
Regression test Why is it kept? To catch working behavior that breaks again
  • The highestScore test is both: it covers one member function and guards a fixed bug.
  • A brand-new test for a new feature is a unit test, not yet a regression test.
  • Comparing a whole program’s output with last week’s output is a regression test, not a unit test.

Regression Testing in Action

Regression testing reruns every existing test after every change. A later cleanup changes the highestScore loop back to i < count - 1.

highestScore loop Test results
Before the cleanup i < count 9 tests run, 0 failed
After the cleanup i < count - 1 9 tests run, 2 failed

The two failures are “highestScore includes the last score” and “scores of exactly 0 and 100 are handled.” Once a bug has a test, it cannot come back without someone noticing. Teams run their regression suites automatically on every change, often on GitHub, so nobody has to remember.

Test a Functor

The same pattern tests the MaxLength functor from 09.01. Each test checks one edge of the limit.

bool testAcceptsExactLimit() {
    MaxLength validUsername(8);
    return check(validUsername("abcdefgh"), "8 characters is accepted");
}

bool testRejectsOneOverLimit() {
    MaxLength validUsername(8);
    return check(!validUsername("abcdefghi"), "9 characters is rejected");
}

bool testAcceptsEmptyString() {
    MaxLength validUsername(8);
    return check(validUsername(""), "an empty string is accepted");
}

All three pass. Full program: cpp/maxlength_tests.cpp

Common Practices

  • Give each test one behavior, and name it after that behavior.
  • Build a new object inside every test so no test can affect another.
  • Work out expected values by hand; never copy them from the code under test.
  • Compare doubles within a tolerance, not with ==.
  • Test through public member functions only.
  • Rerun the whole suite after every change, and add a test for every bug you fix.

Summary

  • A unit test checks one piece of a program against an answer worked out by hand.
  • A regression test is any test kept and rerun to catch working behavior that breaks again; many unit tests are also regression tests.

Key Takeaways

  • A class converts through operator T() or a constructor that takes one value, and both run without being called.
  • Mark conversions explicit unless the target names the meaning and nothing is lost.
  • Return *this by reference when a call changes its object, so chains keep working on the same object.
  • Unit says what a test covers; regression says why you keep rerunning it.

Lambda and Functor Review: Good Practices

  • Prefer a lambda to a functor class that is used once.
  • Capture only the variables the body uses.
  • Capture by value unless the lambda must change or track the original.
  • State the return type when the branches could deduce different types.

Lambda and Functor Review: Common Mistakes

  • Capturing by reference a variable that is gone before the lambda runs.
  • Expecting a by-value capture to see later changes to the original.
  • Changing a by-value capture without mutable.
  • Letting -> int silently drop a fraction.

Lambda and Functor Review: More Examples

                       [passing](int s) { return s >= passing; });
cout << passed << endl;   // 4

Type Conversion Operators: Good Practices

  • Mark conversion operators const.
  • Write a conversion operator only when the result has one obvious meaning.
  • Use a named getter when the unit or meaning could be misread.
  • Give a class at most one conversion to a built-in type.

Type Conversion Operators: Common Mistakes

  • Writing a return type: double operator double() does not compile.
  • Forgetting const, so a const object cannot convert.
  • Adding both operator int() and operator double(), which creates ambiguous calls.
  • Relying on an implicit conversion in a condition, as when zero degrees tested false.

Type Conversion Operators: More Examples

class Percent {
private:
    int points;

public:
    Percent(int value) { points = value; }
    operator double() const { return points / 100.0; }
};

Percent tax(8);
double price = 50.0 * (1 + tax);   // 54

Conversion Constructors: Good Practices

  • Treat every constructor that takes one value as a conversion.
  • Mark it explicit unless the conversion is intended.
  • Check default arguments: a default on the second parameter creates a one-value constructor.

Conversion Constructors: Common Mistakes

  • Adding a default to a second parameter and creating a conversion by accident.
  • Assuming a constructor runs only when it is called by name.
  • Expecting the compiler to chain two user-defined conversions.

Conversion Constructors: More Examples

class Grade {

public:
    Grade(int value = 0) { score = value; }
    int value() const { return score; }

void record(const Grade& g);

record(91);          // 91 becomes a Grade
Grade final = 88;    // 88 becomes a Grade

Object Conversions: Good Practices

  • Write one conversion between any two classes.
  • Put it in the class you own; when you own both, prefer the converting constructor.
  • Keep a conversion implicit only when the target names the meaning and nothing is lost.

Object Conversions: Common Mistakes

  • Writing both a converting constructor and a conversion operator for the same pair of classes.
  • Forgetting that assignment builds a temporary before it assigns.
  • Converting to a bare built-in type that hides the unit.

Object Conversions: More Examples

class Meters {

    double value;

public:
    Meters(double v = 0.0) { value = v; }
    double get() const { return value; }

class Feet {

    double value;

public:
    Feet(const Meters& m) { value = m.get() * 3.28084; }
    double get() const { return value; }
};

Feet height = Meters(2.0);   // 6.56168

Conversion Safety: Good Practices

  • Declare one-value constructors and conversion operators explicit by default.
  • Use = delete to forbid specific argument types.
  • Use static_cast to state an intended conversion.
  • Make operator bool() explicit when it reports whether an object is valid.

Conversion Safety: Common Mistakes

  • Expecting explicit to stop direct initialization such as Roster r(2.7);.
  • Writing a non-explicit operator bool(), so the object can sneak into arithmetic.
  • Leaving both conversion directions implicit and then adding an operator+.

Conversion Safety: More Examples

class Connection {

    bool open;

public:
    Connection(bool state) { open = state; }
    explicit operator bool() const { return open; }
};

Connection link(true);
if (link) { cout << "connected" << endl; }   // allowed
// int n = link + 1;                          // error

Operator Chaining: Good Practices

  • Return *this by reference from =, +=, <<, and setters.
  • Return a new object by value from +, -, and *.
  • Take the right-hand side as const reference.
  • Compile with -Wall so g++ warns about references to locals.

Operator Chaining: Common Mistakes

  • Returning by value from += or a setter, so the next link changes a copy.
  • Returning a reference to a local variable.
  • Returning ostream by value from operator<<.

Operator Chaining: More Examples

// operator+ built from operator+=
Temperature operator+(Temperature lhs, const Temperature& rhs) {
    lhs += rhs;
    return lhs;
}

Temperature t(30.0);
(t -= 5.0) -= 3.0;   // t is 22 when -= returns Temperature&

Unit Testing: Good Practices

  • Write the failing test first, then fix the code.
  • Keep tests fast so running all of them is never a chore.
  • Print each test’s name as it runs so a failure is easy to locate.
  • Set RUN_TESTS back to true and rerun the suite after every change.

Unit Testing: Common Mistakes

  • Sharing one object across tests, so one test’s leftovers change another’s result.
  • Comparing doubles with == instead of within a tolerance.
  • Copying the expected value from the program’s own output, so the test can never fail.
  • Using assert for test checks, which NDEBUG silently removes.
  • Writing a test that breaks a precondition, which aborts the run or, with NDEBUG, corrupts the object being tested.
  • Making data public just so a test can read it.

Unit Testing: More Examples

bool testRemoveLastDecreasesSize() {
    Gradebook book;
    book.addScore(70);
    book.addScore(80);
    book.removeLast();
    return check(book.size() == 1, "removeLast decreases the size by one");
}

bool testCurveNeverExceeds100() {
    Gradebook book;
    book.addScore(99);
    book.addScore(50);
    book.applyCurve(5);

    // Capped curve: 100 and 55, so the average is 77.5
    return check(closeEnough(book.average(), 77.5, 0.001), "a curve never pushes a score past 100");
}
