Relationships

Why Relationships Matter

  • Objects do not work in isolation. They have relationships with each other.
  • We can exploit these relationships to make our code more modular, reliable, and simpler.
  • There are a number of relationships.

Relationship Types

Dependency Relationship

  • The “loosest” form of class relationship.
  • Class A uses Class B temporarily.
  • Also called a “uses-a” relationship.

Coding Characteristics

  • Short-lived interaction.
  • Class A depends on class B, but B is not stored in class A.

Example 1

Example 1: Passing a Document by Reference

#include <iostream>
using namespace std;

class Document {
public:
    string getContent() const {
        return "This is the document content.";
    }
};

class Printer {
public:
    void printDocument(const Document& doc) {  // Dependency
        cout << "Printing: " << doc.getContent() << endl;
    }
};

int main() {
    Document myDoc;
    Printer myPrinter;

    myPrinter.printDocument(myDoc);  // Uses Document temporarily
}

/*
Printer needs to know something about the documents coming in.
That's why we use a reference.
*/

#include <iostream>

int main() {

    Customer c2("Bob");
    Order order;
    order.printCustomerInfo(c1);
    order.sendThankYou(c2);

    return 0;
}

References and Dependencies

  • Do we always need to use reference variables?

Passing by Value

No.

class Logger {
public:
    void logMessage(string message) {  // Passed by value
        cout << "[LOG]: " << message << endl;
    }
};
  • Technically this is a dependency relationship.
  • But because strings are a standard type, nobody thinks of it that way.
  • Nor do we need a reference because strings are built in.

Example 3: Dependency Through a Return Type

#include <iostream>
#include <string>

class User {

    User(string name) : username(name) {}

Memory for an Array of Objects

Array of Objects

 // dsla0.cpp — demo of array of StopLight objects
#include <iostream>
using namespace std;

class StopLight {
public:
    enum Light { RED, YELLOW, GREEN };
    Light steadyLight;

    StopLight() { steadyLight = YELLOW; }
    StopLight(Light lightColor) { steadyLight = lightColor; }
    void cycle();
};

void StopLight::cycle() {
    switch (steadyLight) {
    case RED: cout << "Red\\n"; break;
    case YELLOW: cout << "Yellow\\n"; break;
    case GREEN: cout << "Green\\n"; break;
    }
}

int main() {
    StopLight slArray[2];
    slArray[0].cycle();
    slArray[1].cycle();

    cout << "\\nCreate objects.\\n\\n";

    slArray[0] = StopLight(StopLight::RED);
    slArray[1] = StopLight(StopLight::YELLOW);

    slArray[0].cycle();
    slArray[1].cycle();

    return 0;
}

Key Takeaway

  • Classes are custom types, and we can pass them to methods just like any other type.
  • We need to decide where to instantiate objects: on the stack or the heap.
  • A useful array-of-objects design keeps both the array and its objects on the heap, with the array pointer on the stack.

Resource Acquisition Is Initialization

Why Does Resource Management Matter?

Resource Acquisition Is Initialization ties the lifetime of a resource to the lifetime of an object.

When the object is created, it acquires or takes ownership of a resource. When it is destroyed, it releases that resource automatically.

Slides 40–52

What Is a Resource?

A resource is anything that must be acquired and later released.

  • Dynamically allocated memory
  • Files
  • Mutex locks
  • Threads
  • Database connections
  • Sockets and operating-system handles

Manual Cleanup

#include <cstdio>

FILE* file = fopen("data.txt", "r");
// use file
fclose(file);

This looks simple, but cleanup becomes difficult when a function has multiple return paths or exceptions.

The Leak Risk

void process(FILE* file) {
    if (!read_header(file)) {
        return;  // Did we remember to close the file?
    }

    process_data(file);

    if (something_failed()) {
        return;  // Another possible leak
    }

    fclose(file);
}

If an exception occurs, fclose may never run.

The RAII Solution

Put the resource inside an object whose destructor performs the cleanup.

{
    lock_guard<mutex> lock(mutex);

    update_shared_data();

} // lock is automatically released here

The resource is managed by the object instead of by every control-flow path.

Early Returns and Exceptions

void update(mutex& mutex) {
    lock_guard<mutex> lock(mutex);

    if (some_error()) {
        return;  // Destructor still unlocks the mutex
    }

    do_more_work();
} // Destructor unlocks the mutex

C++ destroys local objects as the stack unwinds, so the destructor still releases the resource.

Standard-Library RAII Classes

C++ already provides many RAII classes.

  • lock_guard and unique_lock manage mutexes.
  • scoped_lock safely locks multiple mutexes.
  • unique_ptr manages dynamically allocated objects.
  • ofstream closes files automatically.
  • jthread handles a thread when it leaves scope.

Ownership Is the Key Question

When designing an RAII class, ask:

Who owns this resource?

  • unique_ptr represents one owner.
  • shared_ptr represents shared ownership.
  • A reference or raw pointer usually represents borrowed access.
  • A custom RAII object can own a specialized resource.

Ownership determines whether the object should be copyable or movable.

Unique Ownership

A unique owner normally cannot be copied, but it can be moved.

#include <memory>
using namespace std;

unique_ptr<int> a = make_unique<int>(42);
// unique_ptr<int> b = a;  // Error

unique_ptr<int> b = move(a);

After the move, b owns the resource and a no longer does.

Custom Resources

RAII is not limited to standard-library resources.

#include <cstdio>
#include <memory>
using namespace std;

struct FileCloser {
    void operator()(FILE* file) const {
        if (file) {
            fclose(file);
        }
    }
};

using FileHandle = unique_ptr<FILE, FileCloser>;

A custom deleter connects a C library resource to a C++ object’s lifetime.

What RAII Does Not Solve

RAII is powerful, but it is not magic.

  • It does not prevent deadlocks caused by poor locking design.
  • It does not prevent cycles created by shared_ptr.
  • It does not fix invalid external state or incorrect ownership decisions.
  • A destructor may not be the right place to report an important failure.

Use an explicit operation such as close or commit when cleanup can fail meaningfully.

Practical Rules

  • Prefer RAII over manual cleanup.
  • Acquire resources close to their first use.
  • Keep the owning scope as small as practical.
  • Make ownership explicit.
  • Use standard RAII classes whenever possible.
  • Use smart pointers instead of raw new and delete.
  • Decide deliberately whether a resource-owning class can be copied or moved.

A resource should have a clear owner, and its owner should automatically release it when its lifetime ends.
