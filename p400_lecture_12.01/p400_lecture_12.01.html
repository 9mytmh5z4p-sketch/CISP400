What Is Overriding?

  • Overriding: a derived class writes its own version of a function it inherited, with the same name, parameters, and const.
  • const is part of the function’s signature, and it does not carry down. Student must write const again, or its print() is a different function.
  • A Student object then uses Student’s version. A Person object still uses Person’s.

The base class is not changed. The derived class replaces the behavior for its own objects only: Person’s print() shows the name and ID, and Student’s shows the name, ID, and major.

If Student writes void print() without const, it is a separate function that hides Person’s print() const. Tested with g++: ava.print() still compiles and runs Student’s version, but calling print() on a const Student, for example through a const Student& parameter, fails with: passing ‘const Student’ as ‘this’ argument discards qualifiers. In 13.02, with virtual functions, a missing const means the function does not override at all.

Animal, Dog, and Cat from 11.02, now with behavior. Every Animal can speak(), and Dog and Cat each write their own speak() with the same name, parameters, and const. A Dog says “Woof, woof,” a Cat says “Meow.”

Overriding Anatomy

class Person {
private:
    string name;
    int id;

public:
    Person(const string& n, int i) : name(n), id(i) { }
    string getName() const { return name; }
    int getId() const { return id; }

    void print() const {
        cout << name << " (" << id << ")" << endl;
    }
};

class Student : public Person {
private:
    string major;

public:
    Student(const string& n, int i, const string& m) : Person(n, i), major(m) { }

    // same name, same parameters, same const: this overrides Person::print()
    void print() const {
        cout << getName() << " (" << getId() << "), " << major << endl;
    }
};

int main() {
    Person lee("Lee", 7);
    Student ava("Ava", 1001, "CS");

    lee.print();    // Person's version
    ava.print();    // Student's version
    return 0;
}

Output: Lee (7) Ava (1001), CS

Student’s print() uses getName() and getId() because name and id are private to Person (11.02, Topic 3). It also repeats the work Person’s print() already does. Topic 2 fixes that.

Overloading vs. Overriding

Overloading Overriding
Where The same class A base class and a derived class
Name Same Same
Parameters Different Same, including const
Which one runs Chosen by the arguments Chosen by the object’s class
Example print() and print(ostream&) in Person Person::print() and Student::print()

Overloading is from the operator overloading and constructor lectures: several functions, one name, told apart by their arguments. Overriding replaces an inherited function for a derived class. The previous slide showed what happens when the two get mixed: a different parameter list in a derived class hides the base version instead of overloading it.

Keep the Promise

class BankAccount {
protected:
    double balance;

public:
    // the promise: never take out more than is there
    bool withdraw(double amount) {
        if (amount > balance) {
            return false;
        }
        balance -= amount;
        return true;
    }
};

class SavingsAccount : public BankAccount {
public:
    // charges a 2.00 fee, but forgot the check
    bool withdraw(double amount) {
        balance -= amount + 2.00;
        return true;
    }
};
  • Both start at 50.00 and try to withdraw 100.00. Checking refuses and stays at 50; savings ends at −52.
  • It compiles. Every caller that trusted withdraw() to refuse is now wrong.
  • Override to change how the request is handled, never what the base promised.

Output of the full program: Checking: 50 Savings: -52

This is the is-a test from 11.02 applied to behavior: a SavingsAccount that can be overdrawn is no longer a BankAccount in the way callers rely on. The fee is a fine reason to override; dropping the check is not. Practice Problem 3 in the appendix asks students to fix it. balance is protected here so the override can change it; 11.02’s advice to keep data private still stands, and Topic 2 shows how calling the base version avoids touching balance at all.

Full program: cpp/broken_promise.cpp

Summary

  • Override an inherited function by writing one with the same name, parameters, and const; the object’s class decides which runs.
  • A different parameter list hides the base version, and an override must keep the base’s promise.

Calling Base Class Functions

Replace or Extend?

  • Topic 1’s Student::print() replaced Person’s version and rebuilt the name and ID by hand.
  • What if Student only wants to add the major?

Slides 20–25

Topic 1 showed the normal case: an override replaces the base version completely. This topic shows the other choice.

Replace vs. Extend

// Replace: Topic 1's version
void print() const {
    cout << getName() << " ("
         << getId() << "), "
         << major << endl;
}
// Extend: run Person's version first
void print() const {
    Person::print();
    cout << ", " << major << endl;
}

Both are overrides of Person::print(); they differ only in the body.

Person:: is the scope resolution operator from member function definitions: it names whose print() to run. Without it, print() inside Student means Student’s own print().

Replace repeats Person’s work, so if Person changes how it prints a name, Student is out of date. Extend reuses it: Student no longer needs getName() or getId() at all. Use extend when the derived class adds to the base behavior, and replace when it truly does something different.

Forgetting Person::

void print() const {
    print();                         // meant Person::print()
    cout << ", " << major << endl;
}
  • It compiles. Running it prints nothing and crashes: Segmentation fault.
  • Without Person::, print() is Student’s own print(), which calls itself until the program runs out of stack.

Tested with g++ 11 and -Wall: no warning, and the program exits with a segmentation fault. clang and g++ 12 or later warn with -Winfinite-recursion that every path through the function calls itself. The crash happens before the first cout, which is why nothing prints.

Keeping the Promise, Fixed

class BankAccount {
private:
    double balance;       // private again

public:
    // the promise: never take out more than is there
    bool withdraw(double amount) {
        if (amount > balance) {
            return false;
        }
        balance -= amount;
        return true;
    }
};

class SavingsAccount : public BankAccount {
public:
    // adds the 2.00 fee, then lets BankAccount do the checking
    bool withdraw(double amount) {
        return BankAccount::withdraw(amount + 2.00);
    }
};
  • Starting at 50.00, withdrawing 100.00 is refused and the balance stays 50. Withdrawing 20.00 is paid and leaves 28.
  • SavingsAccount adds the fee and lets BankAccount do the checking.
  • balance is private again: the override never touches it.

This is Topic 1’s Keep the Promise slide repaired. The fee was a good reason to override; the check had to stay. Calling the base version keeps the check in one place, so a later fix to BankAccount::withdraw() reaches SavingsAccount for free.

Full program: cpp/promise_fixed.cpp

Summary

  • Extend an override by calling the base version, Person::print(), and adding to it; replace it only when the behavior is truly different.
  • Leave off Person:: and the override calls itself until the program crashes.

Multiple Inheritance and the Diamond Problem

Can a Class Have Two Parents?

  • A teaching assistant takes classes and gets paid. Is a TA a Student or an Employee?

Slides 31–40

Run the is-a test both ways: a TA is a Student, and a TA is an Employee. Both pass. C++ lets a class have both parents.

Multiple Inheritance Anatomy

class TeachingAssistant : public Student, public Employee {
Part Meaning
public Student The first parent
, Separates the parents
public Employee The second parent, with its own public
{ ... } The body declares only what a TA adds
  • Leave out the second public and Employee becomes a private parent: 11.02’s Forgot public, in a new place.

A TA gets every public member of both parents. Each parent is listed with its own access specifier; the first public does not carry over to the second.

Multiple Inheritance Anatomy

class Student {
private:
    string name;
    string major;

public:
    Student(const string& n, const string& m) : name(n), major(m) {
        cout << "Student built" << endl;
    }
    string getMajor() const { return major; }
};

class Employee {
private:
    string name;
    double salary;

public:
    Employee(const string& n, double s) : name(n), salary(s) {
        cout << "Employee built" << endl;
    }
    double getSalary() const { return salary; }
};

// two parents, each with its own public
class TeachingAssistant : public Student, public Employee {
public:
    TeachingAssistant(const string& n, const string& m, double s)
        : Student(n, m), Employee(n, s) { }
};

int main() {
    TeachingAssistant sam("Sam", "CS", 1200.00);
    cout << "Major: " << sam.getMajor() << endl;     // from Student
    cout << "Salary: " << sam.getSalary() << endl;   // from Employee
    return 0;
}

Output: Student built Employee built Major: CS Salary: 1200

The constructor passes arguments up to each parent, as in 11.02. The parents are built in the order the class line lists them, Student then Employee, whatever order the initializer list uses. Destruction runs in reverse.

Point out that the name is passed to both parents, so a TA stores it twice. What If Both Parents Are People? comes back to that.

The Escape Hatch: virtual Inheritance

class Student : virtual public Person { ... };
class Employee : virtual public Person { ... };

class TeachingAssistant : public Student, public Employee {
public:
    TeachingAssistant(const string& n, const string& m, double s)
        : Person(n), Student(n, m), Employee(n, s) { }
};
  • Now Person built: Sam prints once, and sam.getName() compiles.
  • This virtual is not Tuesday’s. 13.02’s virtual functions are a different feature that uses the same keyword.

virtual public Person means Student and Employee agree to share one Person part. Because the Person is shared, the most derived class, TeachingAssistant, must build it itself with Person(n); the Person(n) calls inside Student and Employee are skipped when a TA is built. Has-a Instead

class Job {
private:
    string title;
    double salary;

public:
    Job(const string& t, double s) : title(t), salary(s) { }
    double getSalary() const { return salary; }
};

class TeachingAssistant : public Student {     // is a Student
private:
    Job job;                                    // has a Job

public:
    TeachingAssistant(const string& n, const string& m, double s)
        : Student(n, m), job("TA", s) { }

    double getSalary() const { return job.getSalary(); }
};
  • A TA is a Student and has a job.
  • One Person, no ambiguity, no virtual.
  • Output: Sam, CS, paid 1200, with Person built: Sam once.

The is-a and has-a tests from 11.02 settle it: “a TA has a job” is at least as true as “a TA is an employee,” and it removes the diamond. Reach for multiple inheritance only when both is-a sentences hold for everything each parent does. Java and C# allow only one base class for this reason.

Full program: cpp/ta_has_a.cpp

Summary

  • A class can inherit from two parents, each with its own public; a name both parents have is ambiguous until the class overrides it.
  • When both parents share a base, the object holds two copies. virtual inheritance patches it, and has-a usually avoids it.

Key Takeaways

  • Override a function by giving the derived class one with the same name, parameters, and const; a different parameter list hides the base version instead.
  • Extend an override by calling the base version, Person::print(); without Person:: the override calls itself forever.
  • An override changes how a request is handled, never what the base promised.
  • Two parents with a shared base give an object two copies of that base; prefer has-a to a diamond.

Appendix

Overriding Functions: Good Practices

  • Copy the base function’s declaration exactly, then change only the body.
  • Override only when the derived class must handle the same request differently.
  • Keep every promise the base version makes.

Overriding Functions: Common Mistakes

  • Changing the parameter list and hiding the base version instead of overriding it.
  • Leaving off const and getting a second, separate function.
  • Overriding a function so it does something the base version never did.

class Student : virtual public Person {
private:
    string major;

public:
    Student(const string& n, const string& m) : Person(n), major(m) { }
};

class TeachingAssistant : public Student, public Employee {
public:
    TeachingAssistant(const string& n, const string& m, double s)
        : Person(n), Student(n, m), Employee(n, s) { }
};
  • With a virtual base, the most derived class builds it. Student’s Person(n) runs only when a plain Student is built.
