Rule of Five

The Rule of One

One class should have one clear resource-management responsibility. When a class owns a resource, its design must define how ownership begins, changes, and ends.

Slides 56–74 This opening slide recalls the previously introduced Rule of One before extending the idea to copying and moving.

The Rule of One

One class should have one clear resource-management responsibility. When a class owns a resource, its design must define how ownership begins, changes, and ends.

This means we prefer using tools that manage resources for us like smart pointers

Complete Buffer Example

#include <iostream>

using namespace std;

class Buffer {
public:
    Buffer(int size) : data(new int[size]), size(size) {}

    ~Buffer() {
        delete[] data;
    }

    Buffer(const Buffer& other) : data(new int[other.size]), size(other.size) {
        for (int i = 0; i < size; i++) {
            data[i] = other.data[i];
        }
    }

    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            delete[] data;
            size = other.size;
            data = new int[size];
            for (int i = 0; i < size; i++) {
                data[i] = other.data[i];
            }
        }
        return *this;
    }

    Buffer(Buffer&& other)
        : data(other.data), size(other.size) {
        other.data = nullptr;
        other.size = 0;
    }

    Buffer& operator=(Buffer&& other) {
        if (this != &other) {
            delete[] data;
            data = other.data;
            size = other.size;
            other.data = nullptr;
            other.size = 0;
        }
        return *this;
    }

private:
    int* data;
    int size;
};

int main() {
    Buffer first(3);
    Buffer second = first;
    Buffer third(1);
    third = first;
    Buffer fourth = Buffer(4);
    Buffer fifth(2);
    fifth = Buffer(5);
}

This is the complete running example used throughout the topic. Each later slide isolates one part of this class.

One Resource, One Failure

Consider one resource-owning class with the compiler-generated operations.

Buffer first(10);
Buffer second = first;

Memberwise copying gives both objects the same pointer. When both destructors run, the same resource can be released twice.

[Graphic suggestion: show two Buffer objects pointing to one allocation, then show both destructors reaching the same resource.]

From One Failure to Five Responsibilities

The shared-resource failure creates five responsibilities:

  • End ownership when an object is destroyed.
  • Create an independent resource during copy construction.
  • Replace an existing resource during copy assignment.
  • Transfer ownership during move construction.
  • Replace and transfer ownership during move assignment.

Predict which operations the class must control before naming them.

The Five Special Member Functions

  1. Destructor
  2. Copy constructor
  3. Copy assignment operator
  4. Move constructor
  5. Move assignment operator

Destructor: End Ownership

The destructor releases the resource owned by the object. It must leave cleanup with one owner and one matching release operation.

Buffer::~Buffer() {
    delete[] data;
}

Copy Constructor: Create a New Owner

The copy constructor creates independent storage and copies the source contents into it. The source and destination become separate owners.

Buffer::Buffer(const Buffer& other) {
    data = new int[other.size];
    size = other.size;
    // Copy each element from other.data.
}

Copy Assignment: Replace Ownership

Copy assignment replaces the destination’s existing resource with an independent copy of the source resource.

Buffer& Buffer::operator=(const Buffer& other) {
    if (this != &other) {
        delete[] data;
        data = new int[other.size];
        size = other.size;
    }
    return *this;
}

Self-Assignment Must Be Safe

Self-assignment is valid and should leave the object unchanged.

buffer = buffer;

Detect self-assignment before releasing the destination’s resource.

Detecting Self-Assignment

Buffer& Buffer::operator=(const Buffer& other) {
    if (this == &other) {
        cout << "Self-assignment detected\n";
        return *this;
    }

    delete[] data;
    data = new int[other.size];
    size = other.size;
    return *this;
}

Move Constructor: Transfer Ownership

The move constructor transfers the resource instead of allocating a second one. The source must be left in a valid state.

Buffer::Buffer(Buffer&& other) {
    data = other.data;
    size = other.size;
    other.data = nullptr;
    other.size = 0;
}

Move Assignment: Replace and Transfer

Move assignment releases the destination’s current resource, takes ownership of the source resource, and resets the source.

Buffer& Buffer::operator=(Buffer&& other) {
    if (this != &other) {
        delete[] data;
        data = other.data;
        size = other.size;
        other.data = nullptr;
        other.size = 0;
    }
    return *this;
}

Which Operation Does the Call Use?

Predict the operation selected at each call site.

For this prediction, treat each temporary result as if it is moved into its destination. Do not worry about compiler optimizations that might skip a move or copy.

Buffer a;
Buffer b = a;
Buffer c = makeBuffer();
b = a;
b = makeBuffer();

C++ may elide a move in some temporary-return cases. The assumption keeps the instructional focus on the intended move constructor and move assignment operations.

Which Operation Does the Call Use?

The comments identify the operation selected at each call site.

Buffer a;             // Default constructor
Buffer b = a;         // Copy constructor
Buffer c = makeBuffer(); // Move constructor
b = a;                // Copy assignment
b = makeBuffer();    // Move assignment

The Rule of Five in Class Syntax

The five declarations form one ownership contract.

~Buffer();
Buffer(const Buffer& other);
Buffer& operator=(const Buffer& other);
Buffer(Buffer&& other);
Buffer& operator=(Buffer&& other);

Common Practices

Define the five functions when a class directly owns a resource and copying or moving needs special behavior. If the class does not manage a resource directly, prefer a design that lets the compiler manage these operations.

Introduction to Structured Debugging

Where Do You Begin When the Program Is Wrong?

A program can compile and run while still producing the wrong result. Structured debugging turns that failure into a sequence of questions and evidence.

Slides 75–90 This topic introduces the complete debugging process, then develops the first two steps and shows how diagnostics and LLM prompts support the investigation.

Debugging Is Evidence-Based

Debugging is the process of locating the first incorrect state and explaining why it occurred.

Changing code until the output looks right does not show which change repaired the defect. Evidence makes the repair explainable and testable.

The Complete Debugging Process

  1. Establish a reliable starting point.
  2. State the expected behavior.
  3. Reproduce the failure.
  4. Reduce the investigation.
  5. Classify the failure.
  6. Identify the relevant state.
  7. Find the first divergence.
  8. Form one hypothesis.
  9. Design a focused experiment.
  10. Make one focused change.
  11. Verify the repair.
  12. Add a regression test.
  13. Explain the result.

This slide shows the full process. The next slides develop Steps 1 and 2. Later steps become the structure for the Bug Hunt and future debugging work.

Step 1: Establish a Reliable Starting Point

Confirm which source file is compiled, that the program builds, that the input is repeatable, and that compiler warnings are visible.

In production software, preserve evidence and reproduce safely in a test or staging environment whenever possible. Reduce the investigation without experimenting destructively with the live system.

Step 2: State the Expected Behavior

Before studying the implementation, write down what should happen. Use preconditions, postconditions, invariants, expected output, and expected state transitions.

A rejected operation leaves the object unchanged.
A copied object owns independent storage.
A moved-from object remains valid.

Check Results Directly

This function prints whether a Boolean condition passed or failed.

void check(const string& label, bool result) {
    cout << (result ? "PASS: " : "FAIL: ")
         << label << '\n';
}

It is important because it turns an expected behavior into visible evidence. A failed check tells you which expectation needs investigation without requiring you to interpret a large output trace.

Print Pointer Addresses

This function prints the address associated with a pointer or resource handle.

void printPointer(const string& label, const void* address) {
    cout << label << ": " << address << '\n';
}

It is important when ownership or copying is in question. Equal addresses can reveal unintended sharing, while different addresses can support the claim that two objects own independent storage.

Print Relevant Object State

This function prints the values that describe an object at a particular point in the program.

void printState(const string& label, double balance, int count,
                int capacity) {
    cout << label << " balance=" << balance
         << " count=" << count
         << " capacity=" << capacity << '\n';
}

It is important because logic errors often appear as an unexpected change in one field. Printing state before and after an operation helps locate the first broken invariant.

Choosing What to Observe

Diagnostic output should answer a question rather than print everything.

  • Compare state before and after an operation.
  • Compare expected and actual values.
  • Print pointer addresses when ownership is in question.
  • Print counts and capacities at boundaries.

LLM Assistance Begins With Evidence

Give the LLM the context, expected behavior, actual behavior, reproducible test, relevant code, and a specific task.

Ask for analysis before asking for a rewrite. Require line numbers, evidence, and a test that could confirm the hypothesis.

Find the First Divergence

This prompt asks the LLM to identify the first line where actual state can differ from the expected state.

Find the first place where the actual state can diverge
from the expected state. Cite the function and line number.
Do not rewrite the code.
Display the results in the chat window as a markdown table.

It is important because the first incorrect state usually provides stronger evidence than a later symptom. Requiring a location and forbidding a rewrite keeps the LLM focused on analysis.

Extract Formulas and Mutations

This prompt asks the LLM to list every calculation and state change involving the values under investigation.

List every formula and mutation involving balance, count,
capacity, or pointers. Include line numbers and explain
what each operation should preserve.
Display the results in the chat window as a markdown table.

It is important because incorrect arithmetic and accidental state changes can be difficult to spot in a long function. The line numbers and preservation conditions make each operation available for direct review.

Generate Focused Tests

This prompt asks the LLM to turn the suspected behavior into small tests, including an edge case.

Generate three focused tests for this failure, including
one boundary case. Give the expected result and assertion
for each test. Do not modify the implementation.
Display the results in the chat window as a markdown table.

It is important because a test can distinguish a plausible explanation from a confirmed one. Boundary cases also expose assumptions that ordinary inputs may leave hidden.

Bug Hunt Demonstration

BusinessAccount account("Test Customer", 9001);
account.deposit(100.00);

printState("Before withdrawal", account.getBalance(),
           account.getTransactionCount(), 4);

bool result = account.withdraw(0.00);

check("zero withdrawal is rejected", !result);
printState("After withdrawal", account.getBalance(),
           account.getTransactionCount(), 4);

State the expectation, run the smallest test, inspect the first difference, form one hypothesis, and make one focused repair.

Structured Debugging Checklist

  • What should happen?
  • Can the failure be reproduced?
  • What state matters?
  • Where was the first divergence?
  • What hypothesis explains it?
  • What small test can check it?
  • Did the repair preserve earlier behavior?
  • What regression test should remain?
